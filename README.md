# COBOL Game Mainframe

A production-oriented landing page and single-domain gateway for three independent browser games:

- [Trump vs. Shakespeare](https://github.com/Pepitodrop/TrumpVsShakespeare)
- [Crazy Mini Golf](https://github.com/Pepitodrop/CrazyMiniGolf)
- [Crazy Race](https://github.com/Pepitodrop/CrazyRaceGame)

The intended public URL is **`https://game.luisbenedikt.de`**. The launcher is generated from real GnuCOBOL source, while a small Go gateway safely mounts all three unchanged game repositories below one hostname.

## Languages used

### Languages written directly in GamePage

The two implementation languages used directly in this repository are **COBOL** and **Go**.

| Language | Where it is used | Responsibility |
| --- | --- | --- |
| **COBOL** | `src/gamepage.cob` | Generates the launcher HTML, CSS, JavaScript status client, SVG favicon, 404 page, `robots.txt`, and `security.txt` |
| **Go** | `cmd/gateway/` and `internal/gateway/` | HTTP server, reverse proxy, WebSocket forwarding, path rewriting, redirect and cookie rewriting, health aggregation, security headers, logging, and graceful shutdown |

The COBOL generator outputs **HTML**, **CSS**, **JavaScript**, **SVG**, and text files. Those are generated web artifacts rather than separately maintained application source.

The repository also contains deployment configuration written in:

- **Dockerfile syntax** for the multi-stage GamePage image;
- **YAML** for Docker Compose and GitHub Actions;
- **Apache configuration** and a **Caddyfile** for TLS termination and reverse proxying;
- **Bash** for the complete-stack Docker smoke test.

### Languages present in the complete game stack

GamePage does not rewrite the game repositories. Docker builds their existing source exactly as checked out in sibling directories.

| Component | Languages and runtimes | Role in the stack |
| --- | --- | --- |
| **GamePage** | COBOL, Go, generated HTML/CSS/JavaScript/SVG | Launcher and same-domain gateway |
| **Trump vs. Shakespeare** | Python/FastAPI, TrumpScript, Shakespeare Programming Language, GNU Assembly | Room server, game definitions, stage policy, random and combat calculations |
| **Crazy Mini Golf** | Brainfuck, TypeScript, JSON, R, restricted TrumpScript-compatible grammar | Authoritative state transitions, browser game, level data, balancing, optional commentary |
| **Crazy Race** | Rust, R, TrumpScript through Python, Piet, server-rendered HTML/CSS | HTTP server and rules, track generation, announcer, adaptive boost program, browser UI |

### Why the gateway is Go instead of only COBOL

A production WebSocket-aware reverse proxy must handle upgrades, streaming, cancellation, timeouts, forwarding headers, connection pooling, malformed upstream responses, and graceful shutdown. Implementing those details directly in COBOL would require extensive C socket interoperability and would be substantially harder to audit. COBOL therefore owns the complete visible launcher artifact, while Go is restricted to the networking and infrastructure layer.

## What this repository provides

- A responsive game-selection page generated by compiled GnuCOBOL.
- One public hostname with stable paths for all games.
- A Go standard-library reverse proxy with WebSocket support.
- Prefix-safe rewriting for root-relative HTML, CSS, JavaScript, JSON, SVG, redirects, and cookies.
- Live status indicators for all three games.
- A hardened Docker Compose topology.
- Apache and Caddy examples for HTTPS.
- Unit, build, Compose, image, and complete-stack Docker CI checks.
- Deployment, monitoring, update, rollback, security, and troubleshooting guidance.

## Why a gateway is required

The games were originally designed to run at the root of their own origin. Some responses contain URLs such as `/create`, `/api/rooms`, `/ws/...`, or `/assets/...`. A basic reverse proxy mounted under `/play/race/` would therefore send the browser to the wrong root path.

The GamePage gateway solves this without editing the games:

1. It strips the public mount prefix before forwarding a request upstream.
2. It restores the prefix in root-relative textual response URLs.
3. It rewrites upstream `Location` headers.
4. It rewrites cookie `Path` attributes.
5. It preserves WebSocket upgrades.
6. It rewrites Trump vs. Shakespeare WebSocket and share URLs.
7. It disables upstream compression before transforming response bodies.

Example:

```text
Browser POST /play/race/create
             |
             v
Gateway forwards POST /create
             |
             v
Upstream returns Location: /room/ABC123
             |
             v
Browser receives Location: /play/race/room/ABC123
```

## Dockerization

### GamePage image

The GamePage `Dockerfile` is a three-stage build:

1. **COBOL builder:** installs GnuCOBOL, compiles `src/gamepage.cob`, runs it, and verifies the generated assets.
2. **Go builder:** runs the Go test suite and builds a static gateway binary.
3. **Runtime:** copies only the gateway binary and generated site into a non-root distroless image.

The runtime image does not contain the COBOL compiler, Go toolchain, package manager, shell, or source tree.

### Complete Compose stack

`docker-compose.yml` builds four explicit Dockerfiles:

- `GamePage/Dockerfile`
- `TrumpVsShakespeare/Dockerfile`
- `CrazyMiniGolf/Dockerfile`
- `CrazyRaceGame/Dockerfile`

Production controls include:

- only `127.0.0.1:${GAMEPAGE_PORT:-8090}` is published;
- the three games use `expose`, not `ports`;
- all services share an `internal: true` Docker network;
- restart policies and init processes are enabled;
- graceful stop periods are defined;
- root filesystems are read-only where supported;
- writable runtime paths use bounded `tmpfs` mounts;
- the gateway, duel game, and race game drop all Linux capabilities;
- `no-new-privileges` is enabled;
- CPU, memory, PID, connection, room, and log limits are applied;
- every image supplies a health check;
- log rotation is limited to three 10 MB files per service.

The gateway depends on the game containers being **started**, rather than requiring them all to be healthy before it launches. This is intentional: the launcher and status page remain available during a partial game outage, while `/readyz` returns HTTP 503 and identifies the unhealthy game.

## Prerequisites

- Linux server with Docker Engine and Docker Compose v2.
- Git.
- Apache 2.4.47 or newer, or Caddy, for public HTTPS.
- Public ports 80 and 443 available to the host reverse proxy.
- DNS control for `luisbenedikt.de`.
- At least 4 GB RAM recommended for concurrent full-stack builds.

No host installation of COBOL, Go, Rust, Node.js, Python, R, Nginx, TrumpScript, Brainfuck, or Piet tooling is required. The image builds contain their required toolchains.

## First deployment

### 1. Clone all repositories

```bash
sudo mkdir -p /srv/games
sudo chown "$USER":"$USER" /srv/games
cd /srv/games

git clone https://github.com/Pepitodrop/GamePage.git
git clone https://github.com/Pepitodrop/TrumpVsShakespeare.git
git clone https://github.com/Pepitodrop/CrazyMiniGolf.git
git clone https://github.com/Pepitodrop/CrazyRaceGame.git
```

### 2. Configure the stack

```bash
cd /srv/games/GamePage
cp .env.example .env
chmod 600 .env
sed -n '1,200p' .env
```

For production, confirm:

```env
PUBLIC_ORIGIN=https://game.luisbenedikt.de
```

### 3. Validate and build

```bash
docker compose config --quiet
docker compose build --pull
```

On a low-memory server, build sequentially:

```bash
docker compose build gamepage
docker compose build trump-vs-shakespeare
docker compose build crazy-mini-golf
docker compose build crazy-race
```

### 4. Start and wait for health

```bash
docker compose up -d --wait --wait-timeout 240 --remove-orphans
```

### 5. Run the complete Docker smoke test

```bash
bash scripts/docker-smoke-test.sh
```

The smoke test verifies:

- gateway liveness;
- complete readiness;
- the COBOL-generated launcher;
- every `/play/.../` route;
- aggregated healthy status;
- canonical prefix redirects;
- absence of published game ports.

### 6. Inspect the stack

```bash
docker compose ps
docker compose logs --tail=100 gamepage
curl --fail http://127.0.0.1:8090/healthz
curl --fail http://127.0.0.1:8090/readyz
```

Expected behavior:

- `/healthz` returns 200 whenever the gateway is alive.
- `/readyz` returns 200 only when all games are healthy.
- `/readyz` returns 503 with JSON diagnostics when a game is unavailable.
- `/` remains available during a partial game outage.

## DNS

Create:

| Type | Name | Value |
| --- | --- | --- |
| `A` | `game` | Server public IPv4 address |

Add an `AAAA` record only after IPv6 routing, firewall rules, and the host reverse proxy are confirmed working. A broken IPv6 record can make the site appear unavailable for IPv6-capable clients.

Verify:

```bash
getent ahosts game.luisbenedikt.de
```

## Apache deployment

Enable the required modules:

```bash
sudo a2enmod proxy proxy_http proxy_wstunnel rewrite headers ssl
```

Install the bootstrap vhost:

```bash
sudo cp deploy/apache-bootstrap.conf \
  /etc/apache2/sites-available/game.luisbenedikt.de.conf
sudo a2ensite game.luisbenedikt.de.conf
sudo apache2ctl configtest
sudo systemctl reload apache2
```

Request TLS with Certbot:

```bash
sudo certbot --apache -d game.luisbenedikt.de --redirect
```

The HTTPS proxy must forward:

```apache
RequestHeader set X-Forwarded-Proto "https"
```

Use `deploy/apache-https.conf.example` as the reference. Verify:

```bash
curl --fail https://game.luisbenedikt.de/healthz
curl --fail https://game.luisbenedikt.de/readyz
curl -I https://game.luisbenedikt.de/
```

Finally, create a Trump vs. Shakespeare online room and confirm that the second player reaches `Live`. That is the required public WebSocket test.

## Caddy alternative

```bash
sudo cp deploy/Caddyfile /etc/caddy/Caddyfile
sudo caddy validate --config /etc/caddy/Caddyfile
sudo systemctl reload caddy
```

Caddy handles ordinary HTTP and WebSocket proxying to the loopback gateway.

## Continuous integration

### Core CI

`.github/workflows/ci.yml` checks:

1. `go test -race ./...`;
2. `go vet ./...`;
3. GnuCOBOL compilation;
4. generated launcher assets and links;
5. Docker Compose model validity;
6. the complete GamePage image build.

### Complete-stack Docker CI

`.github/workflows/full-stack-docker.yml` additionally:

1. checks out GamePage and the three sibling repositories;
2. validates the resolved Compose model;
3. builds all four Docker images;
4. starts the complete stack and waits for health;
5. runs `scripts/docker-smoke-test.sh`;
6. collects logs on failure;
7. removes containers and volumes afterward.

It runs for relevant pull requests and pushes, can be started manually, and runs weekly to detect compatibility drift in the sibling repositories.

## Security model

- Only the gateway is published, and only on loopback.
- The games are isolated on an internal Docker network.
- Game services cannot be contacted directly from the internet.
- The gateway has fixed upstreams and cannot act as an open proxy.
- Text response rewriting is capped at 16 MiB.
- Runtime containers are non-root where supported.
- Read-only filesystems, bounded temporary filesystems, capability restrictions, and process/resource limits reduce impact from compromise.
- The duel game accepts only the configured public origin.
- TLS terminates at Apache or Caddy.
- `security.txt` directs vulnerability reports to GitHub private vulnerability reporting.

`FORWARDED_ALLOW_IPS=*` applies only to Trump vs. Shakespeare inside the private Compose network. That service has no published port.

## Data and backups

GamePage has no database or persistent volume.

- Mini Golf stores scores in browser Local Storage.
- Trump vs. Shakespeare rooms are held in memory.
- Crazy Race rooms are held in memory.
- Active rooms disappear when their container is replaced.
- A positive `TRACK_SEED` makes race tracks reproducible.

Back up:

```text
/srv/games/GamePage/.env
/srv/games/*/.git
/etc/apache2/sites-available/game.luisbenedikt.de.conf
/etc/letsencrypt/
```

## Rollback

Record all repository commits before updating:

```bash
for repo in GamePage TrumpVsShakespeare CrazyMiniGolf CrazyRaceGame; do
  printf '%-24s ' "$repo"
  git -C "/srv/games/$repo" rev-parse HEAD
done
```

To roll back, check out the recorded commits, rebuild, restart, and rerun the smoke test.

## Troubleshooting

### `/readyz` returns 503

```bash
curl -sS http://127.0.0.1:8090/readyz | python3 -m json.tool
docker compose ps
docker compose logs --tail=200 <service-name>
```

The landing page should still respond on `/`; the readiness JSON identifies the unavailable game.

### Docker cannot find a build context

```bash
ls -la ..
grep '_REPO_PATH' .env
docker compose config
```

Confirm the four sibling directory names and paths.

### Build fails from low memory

Build the services sequentially and inspect resources:

```bash
free -h
df -h
docker system df
```

### Trump vs. Shakespeare never reaches `Live`

Check the public origin, WebSocket forwarding, Apache modules, browser developer tools, and gateway logs:

```bash
sudo apache2ctl -M | grep -E 'proxy|rewrite|headers'
sudo apache2ctl -S
docker compose logs --tail=200 gamepage
```

### A game escapes its `/play/.../` prefix

No game container should publish a host port. Confirm requests pass through GamePage and rerun:

```bash
bash scripts/docker-smoke-test.sh
```

## Known limits

- The stack targets one server and hobby or small-community traffic.
- Active online rooms are not preserved across restarts.
- Horizontal replicas require shared room storage and coordination for the duel and race games.
- The gateway rewrites text-based web content; a future game that embeds root URLs in a binary format may need another rule.
- Final public verification still requires real DNS, TLS, and an external WebSocket room test.
